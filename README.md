Какие эндпоинты (API) нужно реализовать?
Для микросервиса каталога и поиска необходимы две группы эндпоинтов: публичные (для пользователей) и административные (для синхронизации с другими микросервисами или админкой).

Публичное API (Каталог и Поиск)
* GET /api/v1/catalog/categories — Получить дерево категорий.
* GET /api/v1/catalog/products — Получить список товаров с фильтрацией и пагинацией.
    * Параметры: category_id, price_min, price_max, limit, offset.
* GET /api/v1/catalog/products/{product_id_or_sku} — Карточка товара (детальная информация).
* GET /api/v1/search — Полнотекстовый поиск по названию, описанию и характеристикам.
    * Параметры: q (поисковая строка), sort (по цене, по популярности).
* GET /api/v1/catalog/categories/{category_id}/filters — Получить доступные фильтры для конкретной категории (например, если выбрали "Смартфоны", бэкэнд должен вернуть список доступных брендов, объемов памяти и цветов для генерации фильтров на фронтенде).

Внутреннее/Административное API (Управление контентом)
* POST /api/v1/admin/products — Добавить новый товар (вызывается из панели администратора или микросервиса импорта/ERP).
* PATCH /api/v1/admin/products/{id} — Обновить характеристики, цену или остатки товара.
* DELETE /api/v1/admin/products/{id} — Мягкое удаление (деактивация) товара.

Для магазина техники дерево категорий — это иерархическая структура каталога. Техника всегда делится на группы и подгруппы. Например:
* Электроника → Смартфоны и гаджеты → Смартфоны → Apple
* Бытовая техника → Крупная бытовая техника → Холодильники
В базе данных для этого используется связь «один-ко-многим» на саму себя (Self-Referential Relationship). У каждой категории есть поле parent_id, которое указывает на «родительскую» категорию. Если parent_id равен NULL, значит, это корневой раздел.

Параметр remote_side в SQLAlchemy используется для настройки связей с самим собой (Self-Referential Relationships). Он указывает, какая колонка (или список колонок) на «удаленной» стороне связи выступает в роли первичного ключа.

Простыми словами: remote_side=[id] говорит SQLAlchemy, что текущее свойство (parent) ведет вверх по дереву к родительской записи, чей id совпадает с нашим parent_id.

Зачем это нужно?
В обычной связи между двумя разными таблицами (например, User и Post) SQLAlchemy автоматически понимает, где находится первичный ключ (Parent/Primary Key), а где внешний (Foreign Key).
Но когда таблица ссылается сама на себя (как в случае с категориями и подкатегориями), обе колонки находятся в одной и той же таблице. Без remote_side SQLAlchemy не сможет понять:
* Какая сторона связи является «главной» (родителем).
* В каком направлении сопоставлять данные при генерации SQL-запроса JOIN.

back_populates — это параметр в ORM SQLAlchemy (и похожих библиотеках вроде SQLModel), который связывает два свойства relationship() в двунаправленных (бидиректных) отношениях между моделями.

1. Как читается этот составной индекс?
Когда вы создаете индекс вида (is_active, category_id, created_at), PostgreSQL строит древовидную структуру (B-Tree), которая физически отсортирована строго слева направо:
1. Сначала все строки делятся на группы по is_active (сначала все true, потом все false).
2. Внутри группы true строки намертво сортируются по category_id.
3. И только внутри конкретного category_id строки сортируются по created_at.


EXPLAIN ANALYZE SELECT * FROM products
ORDER BY created_at DESC
LIMIT 20 OFFSET 0;


Limit  (cost=825.74..825.79 rows=20 width=649) (actual time=7.301..7.306 rows=20 loops=1)
  ->  Sort  (cost=825.74..836.99 rows=4500 width=649) (actual time=7.299..7.301 rows=20 loops=1)
        Sort Key: created_at DESC
        Sort Method: top-N heapsort  Memory: 66kB
        ->  Seq Scan on products  (cost=0.00..706.00 rows=4500 width=649) (actual time=0.043..2.738 rows=4500 loops=1)
Planning Time: 2.449 ms
Execution Time: 7.486 ms


Анализ лога 
1. Seq Scan on products (Главная проблема) Postgres выполнил последовательное сканирование всей таблицы products. Он прочитал с диска абсолютно все строки (rows=4500 на тот момент, но если их станет 2 000 000, время вырастет линейно с миллисекунд до нескольких секунд).
2. Sort Method: top-N heapsort База данных отфильтровала товары, закинула их в оперативную память и начала сортировать по created_at DESC, чтобы вырезать первые 20 штук (LIMIT 20). Пока в памяти всего 66 кБ данных, это быстро (7.486 ms). Но на 2 миллионах записей этот этап сожрет всю память (переполнит work_mem) и начнет сбрасывать временные файлы на диск, из-за чего всё намертво зависнет на 4 секунды.
Почему именно такой порядок полей в индексе?
Postgres сначала отсечет неактивные товары (is_active), затем быстро найдет нужную категорию (category_id), и так как внутри этой категории данные уже будут физически отсортированы по времени создания (created_at), база просто возьмет первые 20 строк без проведения реальной сортировки в памяти!

EXPLAIN ANALYZE
SELECT * FROM products
WHERE is_active = true AND category_id = '07cab167-ceef-4ab0-a7fc-827006831a14'
ORDER BY created_at DESC
LIMIT 20;

Limit  (cost=0.28..6.05 rows=1 width=649) (actual time=0.496..0.498 rows=0 loops=1)
  ->  Index Scan Backward using ix_products_filtered_list on products  (cost=0.28..6.05 rows=1 width=649) (actual time=0.495..0.496 rows=0 loops=1)
        Index Cond: ((is_active = true) AND (category_id = '07cab167-ceef-4ab0-a7fc-827006831a14'::uuid))
Planning Time: 1.173 ms
Execution Time: 0.613 ms

Execution Time: 0.613 ms: Время выполнения упало с 9.5 мс до 0.6 мс (почти в 15 раз быстрее!). А главное — если вы увеличите таблицу до 2 000 000 записей, это время останется практически таким же (вырастет максимум до 1–2 мс), потому что база делает точечный поиск по дереву индекса.

При маленьком объеме данных LIMIT 20 в связке с top-N heapsort скрывает проблему, создавая иллюзию быстрой работы. Но этот подход не масштабируется, так как база все равно выполняет полный перебор таблицы (Seq Scan). При росте таблицы до миллионов строк этот запрос деградирует из-за дискового ввода-вывода, и только составной индекс гарантирует стабильную скорость \(O(1)\) для выборки первой страницы.
